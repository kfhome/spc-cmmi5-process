# SPC-02 《02-需求开发与管理规程》

> 版本：v1.0　生效日期：2026-09-17　密级：内部　所属体系：软件过程体系（CMMI-L5）

## 1. 目的

规范需求从获取、分析、条目化、评审、基线化到变更、验收的完整生命周期，确保：

1. 每条需求来源清晰、分级明确、编号唯一、可追溯、可测试；
2. 需求变更经过量化影响分析后受控进入基线；
3. 需求缺陷与变更率纳入统计过程控制（SPC, Statistical Process Control），支持组织级过程性能基线（PPB）持续更新；
4. 人类工程师与智能体（Agent）执行同一套需求质量门（QGate），消除"凭印象开发"。

## 2. 适用范围

- 本知识库体系内全部软件项目的需求开发（RD, Requirements Development）与需求管理（REQM, Requirements Management）活动，覆盖新开发、迭代演进、维护修复三类工作。
- 适用主体：产品/需求负责人、开发工程师、测试工程师、QA、承接需求的各类 AI 编码 Agent（Kimi Code、Claude Code 等）。
- 不适用于：纯文档勘误、无功能影响的重构（但仍须遵守 SPC-06 的变更登记要求）。

## 3. 体系定位与 CMMI 实践域映射

本规程处于三级体系第二层：组织级手册（SPC-00 总纲）→ **本规程（SPC-02）** → 模板与检查单（SPC-12，如《需求规格说明书模板》《需求评审检查单》《变更影响分析表》）。

覆盖的 CMMI v3.0 实践域及成熟度等级：

| 实践域 | 等级 | 在本规程的落点 |
|---|---|---|
| RD（需求开发） | 3 级 | 5.2 需求获取与分级、6.1~6.4 需求分析与条目化 |
| REQM（需求管理） | 2~3 级 | 6.5 评审与基线化、6.6 双向可追溯、6.7 变更管理 |
| MA（度量分析）/ OPP（组织过程性能） | 4 级 | 第 8 章需求缺陷密度、变更率的 PPB 与统计控制 |
| CAR（原因分析与解决） | 5 级 | 6.8 需求缺陷根因分析与过程改进回流 |
| OPM（组织性能管理） | 5 级 | 8.4 改进提案遴选与部署 |

## 4. 术语与角色

术语：

- **需求基线（Requirements Baseline）**：经评审批准、纳入配置管理的需求集合，变更须走正式流程。
- **双向可追溯（Bidirectional Traceability）**：正向需求→设计→代码→用例，反向用例→代码→设计→需求，任一环节可互查。
- **PPB**：过程性能基线；**PPM**：过程性能模型；**CI**：配置项；**QGate**：质量门；**Agent**：智能体。

角色 RACI 简表（R=执行 A=批准 C=咨询 I=知会）：

| 活动 | 需求负责人 | 开发（含 Agent） | 测试 | QA | 项目经理 |
|---|---|---|---|---|---|
| 需求获取与分级 | A/R | C | C | I | I |
| 条目化与验收标准编写 | A/R | C | C | I | I |
| 需求评审与基线化 | R | C | R | A（主持） | A |
| 追溯矩阵维护 | A | R | R | C | I |
| 变更影响分析 | R | R | C | C | A |
| 需求缺陷根因分析 | C | R | C | A/R | I |

**Agent 角色定义**：承接任务的 AI 执行体（Kimi Code、Claude Code 等），在需求活动中承担"开发/测试执行者"职责，须遵守与人类相同的 QGate；Agent 无批准权（A），评审批准、基线签发、变更批准只能由人类角色完成。

## 5. 入口准则

满足以下全部条件方可启动需求开发活动：

1. 项目已立项或在迭代计划内，需求来源明确（合同、用户反馈、组织战略、缺陷根因分析输出之一）；
2. 项目裁剪级别已按第 9 章确定（微型/标准/大型高风险）；
3. 需求管理工具或存储约定就绪：Markdown 需求库 + 唯一编号空间 + 追溯矩阵文件（见 6.2）；
4. 需求负责人已指定且未被其他 A 级批准职责冲突占用。

## 6. 过程活动

### 6.1 需求获取与来源登记

- **输入**：合同/任务书、用户反馈、组织过程资产、CAR 改进提案。
- **执行要点**：
  1. 每条原始诉求登记到《需求来源登记表》（SPC-12 模板 TPL-R-01），记录来源、提出人、日期、原始表述原文（不改写）；
  2. 来源不明或口头传达的需求，须在登记前向提出人书面确认一次，确认记录附在登记条目下；
  3. 涉多项目的共性需求标记"候选组织级资产"，抄送过程资产组。
- **输出**：需求来源登记表（CI）。
- **责任**：需求负责人 R/A。

> 🤖 智能体执行要点：Agent 接到任务时**第一步必须是定位需求条目**——在需求库中检索编号，读取该条目的原始表述、验收标准、追溯链接；找不到对应条目时不得动手，立即走 6.1.2 升级路径，禁止"按对话上下文脑补需求"直接编码。

### 6.2 需求分级与条目化

- **输入**：需求来源登记表。
- **执行要点**：
  1. 按四级分级：**业务需求（BR）**——组织/商业目标；**用户需求（UR）**——用户场景与目标；**功能需求（FR）**——系统应做什么；**非功能需求（NFR）**——性能、安全、可用性、兼容性等质量属性。每条 BR 至少分解到 UR，每条 UR 至少分解到 FR 或 NFR；
  2. 唯一编号规则：`REQ-<项目码>-<级别>-<四位序号>`，如 `REQ-APS-FR-0031`；编号一经分配永不复用，作废需求标 `[已作废]` 保留占位；
  3. 每条 FR/NFR 条目必须包含字段：编号、标题、分级、来源链接、详细描述、**验收标准（见 6.4）**、优先级（MoSCoW：Must/Should/Could/Won't）、状态（草稿/评审中/已基线/已变更/已作废）；
  4. NFR 必须量化：不写"响应快"，写"P95 接口响应 ≤ 500ms（并发 200，数据量 10 万行）"。
- **输出**：需求规格说明书（含条目化清单，CI）。
- **责任**：需求负责人 A/R，开发 C。

### 6.3 需求分析与冲突消解

- **输入**：条目化需求清单。
- **执行要点**：
  1. 逐条检查：完整性（有验收标准）、一致性（与其他条目不矛盾）、可行性（技术可达成）、必要性（能反查到上级 BR/UR）；
  2. 条目间冲突、需求与既有系统行为冲突，登记《需求冲突清单》，由需求负责人在评审前逐条裁决，裁决理由写入条目历史；
  3. 对关键 FR 做接口/数据流预分析，识别对既有 CI 的影响面，提前告知开发。
- **输出**：需求冲突清单及裁决记录、可行性批注。
- **责任**：需求负责人 R，开发 C。

> 🤖 智能体执行要点：Agent 在阅读需求时发现以下任一情形必须停止并升级，不得自行裁量：①两条需求逻辑矛盾；②验收标准缺失或不可测；③需求与既有代码行为冲突但无迁移说明。升级路径：在任务记录中写明冲突条目编号与歧义点 → 提交需求负责人裁决 → 获得书面裁决（会议纪要/登记条目更新）后方可继续。

### 6.4 验收标准编写（可测试性要求）

- **输入**：条目化需求。
- **执行要点**：每条 FR/NFR 的验收标准采用 **Given-When-Then** 或"条件-动作-判据"句式，且满足：
  1. 可判定：存在明确通过/失败判据，禁止"基本正常""用户体验良好"类表述；
  2. 可执行：测试工程师或 Agent 不依赖额外口头解释即可写出测试用例；
  3. 有边界：正常值、边界值、异常值至少各一条（Must 级需求强制）。
- **输出**：验收标准内嵌于需求条目（CI）。
- **责任**：需求负责人 R，测试 C。

### 6.5 需求评审与基线化

- **输入**：需求规格说明书草稿、冲突裁决记录。
- **执行要点**：
  1. 正式评审会议（微型项目可裁剪为异步评审，见第 9 章），参会角色至少含需求负责人、开发代表、测试代表、QA；
  2. 使用《需求评审检查单》（SPC-12 模板 CHK-R-02）逐项过检：分级正确、编号合规、验收标准可测、追溯关系完整、冲突已清零；
  3. 评审缺陷逐条记录（条目编号+缺陷类型+严重度），返修后由 QA 复核关闭；
  4. 评审通过后由 QA 与项目经理双签批准，需求集纳入配置库并打基线标签（如 `BL-REQ-v1.0`），此后变更走 6.7。
- **输出**：评审记录、已基线需求集（CI，带基线标签）。
- **责任**：QA A（主持），需求负责人 R，项目经理 A。

> 🤖 智能体执行要点：Agent 可作为评审参与者做**预检**：评审前自动执行检查单中可自动化的项（编号格式、必填字段完整性、追溯链接存活、验收标准句式匹配），输出预检报告供人类评审聚焦逻辑性问题。Agent 不具备批准权，不得代替双签。

### 6.6 双向可追溯性维护

- **输入**：已基线需求集。
- **执行要点**：
  1. 建立《需求追溯矩阵》（SPC-12 模板 TPL-R-03）：行=需求编号，列=设计元素（SPC-04 产物）、代码模块/提交、测试用例（SPC-05 产物）、状态；
  2. 正向追溯：每条已基线需求必须能追到至少一个设计元素和一个测试用例；反向追溯：每个测试用例、每次需求相关代码提交必须标注需求编号（提交信息约定：`[REQ-XXX-FR-0001] 提交说明`）；
  3. 每次迭代结束前做一次追溯完整性扫描：孤儿代码（无需求编号的功能性提交）、悬空需求（无实现无测试的已基线条目）均列入缺口清单；
  4. 缺口清单是迭代回顾的固定议题，缺口未清零不得宣布迭代需求完成。
- **输出**：需求追溯矩阵（CI）、追溯缺口清单。
- **责任**：开发/测试 R，需求负责人 A。

> 🤖 智能体执行要点：Agent 提交代码时必须在提交信息首行写入需求编号；新建测试用例时必须回填追溯矩阵对应单元格。交付前自查：本次改动涉及的每个需求编号在矩阵中"设计/代码/用例"三列均已更新，未更新则交付不完整。

### 6.7 需求变更影响分析流程

- **输入**：变更请求（CR，任何干系人均可提出）。
- **执行要点**（基线后变更一律走本流程，禁止口头变更）：
  1. 登记 CR：编号 `CR-<项目码>-<三位序号>`，附变更理由与期望内容；
  2. 影响分析（由需求负责人组织，开发/测试参与）：借助追溯矩阵确定受影响的设计元素、代码模块、测试用例清单；估算工作量变化、进度影响、对其他需求的连锁影响；填写《变更影响分析表》（SPC-12 模板 TPL-R-04）；
  3. 分级审批：影响工作量 ≤ 2 人日且不影响其他需求——项目经理批准；否则提交变更控制委员会（CCB，见 SPC-06）；
  4. 批准后更新需求条目（版本号+1、状态置"已变更"、保留历史版本）、同步追溯矩阵与相关 CI；拒绝的 CR 记录拒绝理由闭环；
  5. 变更引起的返工工时单独记录（度量项 M-05 数据源）。
- **输出**：CR 记录、变更影响分析表、更新后的基线。
- **责任**：需求负责人 R，项目经理/CCB A，QA C。

### 6.8 需求缺陷根因分析（CAR）

- **输入**：评审缺陷记录、验收阶段的需求类缺陷（理解偏差、遗漏、歧义导致）、变更返工数据。
- **执行要点**：
  1. 每月由 QA 汇总需求类缺陷，按缺陷类型分类计数（遗漏/歧义/不一致/不可测/越界镀金）；
  2. 占比超 PPB 控制上限或单月 Top1 类型占比 ≥ 30% 时启动 CAR（SPC-09）：鱼骨图/5-Why 定位过程根因，形成纠正与预防措施；
  3. 措施涉及过程文件修改的，回流到本规程或 SPC-12 模板更新；涉及工具/自动化的，立项部署（OPM 通道，见 8.4）；
  4. 典型根因与对策沉淀为《需求常见缺陷模式库》，作为评审检查单与 Agent 提示词的更新源。
- **输出**：根因分析报告、过程资产更新记录。
- **责任**：QA A/R，过程资产组 C。

## 7. 出口准则与质量门

需求活动各 QGate 通过条件（全部满足方可放行）：

- **QGate-R1（条目化完成）**：来源登记 100%；每条需求编号唯一且字段齐全；NFR 全部量化。
- **QGate-R2（基线化）**：评审缺陷全部关闭；检查单全项通过；双签批准完成；基线标签已打。
- **QGate-R3（移交开发）**：追溯矩阵中每条 Must/Should 需求已有设计元素与测试用例占位；无未裁决冲突；验收标准经测试代表确认可执行。
- **QGate-R4（迭代收口）**：追溯缺口清单清零；本期变更 100% 走完 6.7 流程；需求类缺陷数据已报度量库（SPC-08）。

## 8. 度量指标与量化要求

### 8.1 度量项与计算口径

| 编号 | 指标 | 口径 | 数据源 |
|---|---|---|---|
| M-01 | 需求缺陷密度 | 评审+验收发现的需求类缺陷数 ÷ 已基线需求条目数 | 评审记录、缺陷库 |
| M-02 | 需求变更率 | 本期批准 CR 数 ÷ 期初基线需求条目数 | CR 记录 |
| M-03 | 返工占比 | 需求变更引起的返工工时 ÷ 项目总工时 | 工时记录 |
| M-04 | 追溯完整率 | 三列齐全的矩阵行数 ÷ 已基线条目数 | 追溯矩阵扫描 |
| M-05 | 验收标准一次可测率 | 测试代表一次性确认可执行的条目数 ÷ 送审条目数 | QGate-R3 记录 |
| M-06 | 歧义升级响应时长 | Agent/开发提交歧义升级 → 获得书面裁决的耗时（中位数） | 任务记录 |

### 8.2 统计过程控制

- QA 每迭代采集上述数据，落入度量库（建议位置：`度量库/需求域/<项目码>.csv`，汇总口径由 SPC-08 统一规定）。
- M-01、M-02 按项目迭代打点绘制控制图（XmR 单值-移动极差图）：连续 8 点同侧、单点超 ±3σ、或 6 点连续上升即触发异常信号分析。
- 组织级 PPB 每季度由过程资产组用近 12 个月全项目数据重算，发布新版本（含均值与控制限）。示例基线（组织历史数据首版，待实际数据校准）：M-01 ≤ 0.15 条/条目（UCL 0.30）；M-02 ≤ 8%/迭代（UCL 15%）；M-04 ≥ 95%。

### 8.3 过程性能模型（PPM）应用

- 建立预测模型：`验收阶段需求类缺陷数 ≈ f(评审缺陷密度, 验收标准一次可测率, 变更率)`，用组织历史数据回归拟合；项目策划阶段（SPC-03）用 PPM 预测验收缺陷区间，实际值落在预测区间外时触发原因分析。
- M-06 用于量化 Agent 协同质量：中位数 > 1 个工作日时，分析是否因需求条目质量不足，回流改进 6.2/6.4。

### 8.4 持续优化回流（OPM）

- 每季度过程资产组评审度量趋势与 CAR 产出，遴选改进提案（如：新增编号自动校验脚本、验收标准句式检查器、追溯矩阵自动扫描器）；
- 入选提案先在一个试点项目部署并度量收益（前后对比 M-01/M-04），显著改进（达到统计显著或实用显著阈值）后推广至组织级并更新本规程与模板。

## 9. 裁剪指南

| 维度 | 微型项目（≤2 人月/低风险） | 标准项目 | 大型/高风险项目 |
|---|---|---|---|
| 来源登记 | 简化为任务清单中"来源"一列 | 完整登记表 | 完整登记表+干系人访谈纪要 |
| 分级 | UR/FR 两级即可 | 四级全用 | 四级全用+NFR 单独章节 |
| 评审 | 异步评审（文档评论+QA 单签） | 正式会议+双签 | 正式会议+双签+外部干系人参与 |
| 追溯矩阵 | 需求↔用例两列 | 全四列 | 全四列+自动化扫描脚本强制接入 |
| 变更审批 | 项目经理一级审批 | 分级审批 | 全部走 CCB |
| 度量 | 仅 M-01/M-04 | 全六项 | 全六项+控制图逐迭代评审 |
| 最小执行集 | 编号唯一、验收标准可测、提交带需求编号、变更登记 | —— | —— |

裁剪决策记录到项目计划（SPC-03），QA 审计时按裁剪后口径判定合规性。
