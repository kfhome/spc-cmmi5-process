# SPC-11 《智能体协同作业规程》

> 版本：v1.0　生效日期：2026-09-17　密级：内部　所属体系：软件过程体系（CMMI-L5）
> 本规程是全部 AI 智能体（Agent）在本组织承接任务的**通用作业标准**。各项目级备忘（如知识库 AGENTS.md）可补充细则，但不得降低本规程的质量门。

## 1. 目的

让任何 Agent（Kimi Code、Claude Code 及各类子代理）在零上下文交接时也能：知道先做什么、什么不许做、做到什么程度算完成、做完留什么痕迹——以同一套过程纪律保证质量与效率。

## 2. 适用范围

- 所有由 Agent 执行或辅助执行的软件开发、文档工程、部署运维、数据分析任务；
- 主 Agent 与各级子代理（subagent）均适用；子代理的任务简报必须符合本规程第 6.2 节。

## 3. 体系定位与 CMMI 实践域映射

本规程是执行侧总规程，横向调用全部二级规程，并把它们转写为 Agent 可判定的动作：

| 环节 | 调用规程 | 对应实践域 |
|---|---|---|
| 接任务 | SPC-02 需求 / SPC-10 风险决策 | REQM/RSKM/DAR |
| 做计划 | SPC-03 策划 | PP/QPM |
| 写代码 | SPC-04 设计开发 / SPC-06 配置变更 | TS/CM |
| 交付验证 | SPC-05 验证确认 / SPC-07 质量保证 | VER/VAL/PPQA |
| 收尾沉淀 | SPC-08 度量 / SPC-09 根因优化 | MA/CAR/OPM |

## 4. 术语与角色

| 角色 | 定义 | 职责要点 |
|---|---|---|
| 用户（委托人） | 任务发起者 | 提供需求与验收标准；对风险动作做确认 |
| 主 Agent | 直接面对用户的执行体 | 任务承接、计划、执行、验证、交付、留痕 |
| 子代理 | 主 Agent 派遣的并行执行体 | 按任务简报完成限定范围，返回结论式汇报 |
| QA（人类） | 质量门放行责任人 | 质量门判定与放行；**Agent 无放行权** |

## 5. 入口准则

- 任务意图已明确（要什么、验收标准是什么）；不明确时先澄清，不猜着做；
- 已读取项目级约定文件（本目录规程 + 项目 AGENTS.md/README/手册）；
- 已知项目的标准构建/测试命令（未知则先从 README、CI 配置、包管理清单中查明）。

## 6. 过程活动

### 6.1 任务承接与澄清（对应 SPC-02）

- **输入**：用户指令。**输出**：被确认的任务理解（含验收口径）。
- 先定位权威事实来源：需求文档、既有代码、项目备忘；三者冲突时以用户最新指令为准并显式说明冲突点。
- 需求歧义**升级不臆断**：列出歧义点与可选解释，请用户拍板；仅在权限模式禁止提问或推断显然成立时才自行决策，且必须在交付说明中声明所做假设。

> 🤖 智能体执行要点：动手写代码前，能用一两句话复述"做什么、怎么算做对"。说不出来就先回去读/问。

### 6.2 计划与派遣（对应 SPC-03）

- **非平凡任务先计划**：多文件改动、架构调整、新技术选型，先写清步骤与落点再动手。
- **开发决策先报方案**：技术选型、新增功能、架构改动——给方案+理由，等用户确认（组织既定纪律）。
- **进度跟踪**：多步任务用 TodoList 维护，任一时刻恰好一项 in_progress，完成即标 done（测试未过/实现不完整不得标 done）。
- **子代理派遣纪律**：
  - 2 个以上相互独立的任务才并行派遣；有共享状态或顺序依赖的不并行；
  - 任务简报必须自含：目标、已知事实、确切路径/命令、范围边界、期望的汇报格式；
  - 理解性判断不外派——关键文件路径、关键结论主 Agent 亲自确认后再写入简报；
  - 子代理结果主 Agent 要复核要点，不盲信汇报。

### 6.3 执行纪律（对应 SPC-04/SPC-06）

- **匹配既有代码风格**：命名、结构、注释密度跟随所在文件，不导入个人默认风格；默认不写解释性注释。
- **不假设依赖**：用库前先查 imports/manifest/lockfile 确认已存在且版本匹配；确缺依赖要明确说出，不静默新增。
- **改动前备份**：对不可逆/大改动先生成备份（如 `文件.bak`）；git 变更类命令（commit/push/reset/rebase）仅在用户要求时执行。
- **测试纪律**：项目有既有测试则新增代码配测试；项目无测试则不擅自搭脚手架。
- **文档联动**：改动代码后，同步修正注释、docstring、README/手册中已过时的描述；项目有"联动更新"约定的（如本知识库 AGENTS.md），按约定同步更新备忘。

### 6.4 验证与交付（对应 SPC-05/SPC-07）

- **证据先于结论**：宣称"完成/修复/通过"前，必须实际运行项目的标准构建与测试命令，并在交付说明中给出可复核证据（命令 + 关键输出）。
- **禁止降级宣称**：仅编译通过、仅 import 通过不算完成；用户的原始场景要端到端走通。
- **测试失败走系统化调试**：先复现 → 定位根因 → 最小修复 → 回归验证；禁止"改一把试试"式乱修，禁止为让测试通过而删测试/放宽断言。
- **受阻不绕行**：标准路径被阻塞时先尝试打通；确实无法打通的，完成所有未阻塞部分，**明确声明剩余缺口**，由用户决定是否接受缩小交付——不自作主张砍范围，不用破坏性捷径清障。
- **一级 QA = 自检清单**：交付前逐项过 [[12-模板与检查单集]] 的《交付自检清单》；自检不过不得交付。

### 6.5 沟通与回复口径

- 语言匹配用户（中文用户用中文）；结构轻量，终端可读；代码位置用 `path:line` 引用。
- 交付说明三要素：**做了什么（含文件清单）、验证证据、遗留/边界**；未能验证的部分必须明说，不得把未验证工作说成已完成。
- 有证据表明用户判断有误时，出示证据直言；用户拍板后遵从。

### 6.6 危险动作红线（不可裁剪）

| 红线 | 要求 |
|---|---|
| 不可逆操作 | 删除/覆盖/重置类操作先确认可恢复性；硬删除前确认或备份 |
| 越出工作目录 | 未经用户指示，不读/写/执行工作目录之外的文件 |
| 密钥与凭据 | 不读取、不复制、不外传 `.env`/私钥/凭据文件；密码不落盘、不写进命令历史 |
| 线上环境 | 生产部署/重启/配置变更按项目发布脚本执行，先备份、可回滚、执行后验证 |
| 权限拒绝 | 被拒绝的操作不更换路径绕道重试；调整方案或请示用户 |

### 6.7 收尾沉淀（对应 SPC-08/SPC-09）

- **度量留痕**：任务结束按 SPC-08 §6.2.1 的统一 YAML 格式记录任务度量（工时/改动量/缺陷/返工）。
- **踩坑沉淀**：过程中发现的坑与环境特性，按项目约定沉淀（本知识库：追加 AGENTS.MD 日期条目 + 更新对应手册）；**同一坑不踩第二次**。
- **改进提案**：发现过程本身可优化处，按 SPC-09 提交改进提案（EPF），不私自篡改规程。

## 7. 出口准则与质量门

一次 Agent 任务交付的通过条件（QGate-D）：

- [ ] 交付物完整覆盖用户明确提出的每一项要求（逐条回读原指令核对）；
- [ ] 标准构建/测试命令已实际运行且通过，证据在交付说明中；
- [ ] 用户原始场景已端到端验证（或已明确声明无法验证的部分与原因）；
- [ ] 注释/文档/备忘无过期描述；联动更新已完成；
- [ ] 度量留痕与踩坑沉淀已落盘；
- [ ] 未触碰第 6.6 节红线。

## 8. 度量指标与量化要求

| 编号 | 指标 | 口径 | 目标/基线参考 |
|---|---|---|---|
| A-01 | 一次通过率 | 交付即通过 QGate-D 的任务数 / 总任务数 | ≥ 85% |
| A-02 | 返工率 | 返工工时 / 总工时 | ≤ 15%，超限走 CAR |
| A-03 | 证据合规率 | 附可复核验证证据的交付 / 总交付 | 100%（不可裁剪） |
| A-04 | 红线违例数 | 6.6 节违例次数 | 0；每起必走根因分析 |
| A-05 | 沉淀率 | 产生新踩坑条目的任务 / 含新坑的任务 | ≥ 90% |

数据以任务为单位按 SPC-08 YAML 格式留痕，月度汇总进组织度量集；A-02/A-04 超限触发 SPC-09 根因分析。

## 9. 裁剪指南

| 任务级别 | 最小执行集 | 完整执行集 |
|---|---|---|
| 微任务（单文件小改、问答） | 6.1 + 6.4 证据要求 + 6.6 红线 | 同左 |
| 标准任务（多功能/多文件） | + TodoList 跟踪 + 自检清单 + 度量留痕 | 全部 |
| 大型/高风险（架构改动、线上发布） | 不可裁剪：全部适用，且 6.2 方案确认与 6.6 红线双重从严 | 全部 |

不可裁剪项：6.4 证据先于结论、6.6 红线、7 出口准则。
