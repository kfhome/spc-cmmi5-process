# SPC-04 《04-设计开发与产品集成的过程》

> 版本：v1.0　生效日期：2026-09-17　密级：内部　所属体系：软件过程体系（CMMI-L5）

## 1. 目的

规范从架构设计到产品集成全过程的活动、产出物与质量门，确保：

1. 架构决策可追溯（ADR，Architecture Decision Record），技术选型经决策分析与决议（DAR）流程；
2. 详细设计达到可执行颗粒度，人类工程师与 Agent 均可直接按图施工；
3. 编码、静态检查、代码评审、接口契约与产品集成均有可判定的通过标准；
4. 设计开发过程的度量数据可采集、可统计控制，支撑成熟度 5 级的量化优化。

## 2. 适用范围

- 本组织内全部软件开发项目与维护性变更的设计、编码、集成活动。
- 执行主体为人类工程师、AI 编码 Agent（Kimi Code、Claude Code 等）及其混合编队。
- 技术方案选型、重大架构变更须联动 SPC-10《风险与决策管理》的 DAR 流程；需求基线以 SPC-02 输出为准；验证活动衔接 SPC-05；配置与变更控制衔接 SPC-06。

## 4. 术语与角色

术语：

- ADR：架构决策记录，一份一个决策的轻量文档，含背景、选项、结论、后果。
- DAR：决策分析与决议流程，见 SPC-10。
- PPB：过程性能基线；PPM：过程性能模型；CI：配置项；QGate：质量门；Agent：承接任务的 AI 执行体。
- 接口契约：两个组件/服务间关于协议、数据格式、错误码、版本策略的书面约定。

角色（RACI 简表，R=执行 A=批准 C=咨询 I=知会）：

| 角色 | 架构设计 | 详细设计 | 编码 | 评审 | 集成 |
| --- | --- | --- | --- | --- | --- |
| 架构师 | A/R | C | I | C | C |
| 开发工程师 | C | R | R | R | R |
| Agent | C | R（受监督） | R（受监督） | R（初审） | R（脚本执行） |
| 评审负责人 | I | A（评审结论） | I | A | I |
| 集成负责人 | I | I | I | I | A/R |
| QA（SPC-07） | I | C | C | C | C |

Agent 角色定义：承接任务的 AI 执行体，须遵守与人类相同的质量门；其产出物的批准人（A 角色）始终为人类，不得由 Agent 自审自批。

## 5. 入口准则

满足以下全部条件方可进入设计开发：

1. 需求已基线化并通过 SPC-02 的评审 QGate，需求条目有唯一编号；
2. 项目计划（SPC-03）已含设计与集成阶段的里程碑、工时与度量计划；
3. 开发环境与集成环境可用（代码库可写、CI 流水线可运行、测试环境可部署）；
4. 既有代码与文档可被读取（Agent 须能访问仓库与项目说明文件）；
5. 若涉及技术选型或架构变更，DAR 触发条件已按 SPC-10 识别并登记。

## 6. 过程活动

### 6.1 架构设计与决策记录（ADR）

- 输入：需求基线、既有架构文档、约束清单（性能/安全/合规）。
- 执行要点：
  1. 产出或更新架构说明文档（组件视图、部署视图、数据流视图至少各一）；
  2. 每个"有备选方案且影响跨越一个模块"的决策必须落一份 ADR，存放于项目 `docs/adr/` 或知识库对应目录，命名 `ADR-NNNN-标题.md`；
  3. ADR 内容四段式：背景与约束 / 备选方案及对比 / 决策结论 / 后果与回退条件；状态取值：提议/已接受/已废弃/被 ADR-XXXX 替代；
  4. 技术方案选型（语言、框架、数据库、第三方服务、架构风格变更）一律走 SPC-10 的 DAR：先定义评价准则与权重，再评分，决议结果回填 ADR；禁止未经 DAR 直接引入新框架。
- 输出：架构说明文档、ADR 集合、DAR 决议记录（选型类）。
- 责任角色：架构师 A/R，开发工程师 C。

> 🤖 智能体执行要点
> - 动手设计前先读：项目 README/AGENTS.md、既有 `docs/adr/` 全部未废弃 ADR、目标模块的现有代码；
> - 新决策不得与已接受 ADR 冲突；确需推翻旧决策时，新建 ADR 并将旧 ADR 状态改为"被 ADR-XXXX 替代"，不得删除；
> - 不得在 ADR 之外的地方隐式做架构决策（如直接换库、改协议而不留记录）。

### 6.2 详细设计（最低颗粒度）

- 输入：架构说明、ADR、需求条目编号清单。
- 最低颗粒度要求（缺一即不得进入编码）：
  1. 每个需求条目可映射到具体的类/函数/接口，映射表随设计文档交付；
  2. 公开接口（跨模块/跨服务）须给出：函数签名或 API 路径、入参出参类型与取值约束、错误码表、前置/后置条件；
  3. 非平凡算法（分支数 >5 或含并发/事务/状态机）须给伪代码或流程图；
  4. 数据模型变更须给字段级定义（名称、类型、约束、默认值、迁移策略）；
  5. 异常路径设计：每个外部调用点标明超时、重试、降级策略。
- 输出：详细设计文档（按 [[12-模板与检查单集]]《详细设计模板》）、需求-设计映射表。
- 责任角色：开发工程师/Agent R，架构师 C，评审负责人对评审结论 A。

> 🤖 智能体执行要点
> - 详细设计是 Agent 编码的唯一依据；颗粒度不足时 Agent 必须先补齐设计或退回澄清，禁止"边猜边写"；
> - 设计中的接口签名、字段名、错误码与实际代码逐字一致；编码中偏离设计处，先改设计文档再改代码（或同提交内一并修改）。

### 6.3 编码规范与静态检查

- 输入：详细设计文档、项目编码规范、既有代码库。
- 执行要点：
  1. 编码规范遵循项目仓库内已有约定（lint 配置、格式化配置、AGENTS.md 风格条款）；无既有约定的新项目，按 [[12-模板与检查单集]]《编码规范基线》建立；
  2. 提交前必须通过项目标准检查：构建命令 + 静态检查（lint/typecheck）+ 单元测试，三者均为项目工具链默认命令，不得跳过；
  3. 注释只写"为什么"，不复述代码；公开接口必须有文档注释（参数、返回、异常）；
  4. 禁止引入未在详细设计或 ADR 中确认的第三方依赖（见 6.5 接口契约）；确需新增依赖，先补 DAR/ADR 再改 manifest；
  5. 安全基线：不硬编码密钥、不提交凭据文件、外部输入必须校验、日志不输出敏感数据。
- 输出：源代码（CI）、静态检查通过记录、单元测试通过记录。
- 责任角色：开发工程师/Agent R。

> 🤖 智能体执行要点
> - 匹配既有代码风格：先读同目录/同模块代码，沿用其命名、结构、错误处理与测试写法，不导入个人默认风格；
> - 不假设依赖：仅使用项目 manifest（pom.xml/package.json/pubspec.yaml 等）中已声明的库；认为缺少能力时，在任务记录中写明并停止该路径，不得静默新增依赖；
> - 交付前必须运行项目标准构建/测试命令，把命令与结果（通过/失败摘要）写入任务记录；测试红时不得宣称完成；
> - 改动后同步更新注释与文档：行为变化涉及的注释、docstring、README/手册在同一次提交内更新；发现注释描述的是旧行为，一并修正；
> - 不执行破坏性动作（删文件、改数据库、动 CI 配置）除非任务明确授权。

### 6.4 代码评审

- 输入：待评审代码（提交/合并请求）、详细设计、静态检查结果。
- 触发条件（满足任一即必须评审，不得豁免第 1 条）：
  1. 所有进入主干/发布分支的代码；
  2. 修改公开接口或接口契约（触发 6.5 的契约评审）；
  3. 涉及安全、并发、事务、数据迁移的改动；
  4. 单次改动超过 400 有效行或跨 3 个以上模块；
  5. 修复 P1/P2 级缺陷（须复现根因说明，衔接 SPC-09）；
  6. Agent 产出的代码：必须由人类评审后方可合并（Agent 可先做机器初审）。
- 执行要点：评审用 [[12-模板与检查单集]]《代码评审检查单》（正确性/与设计一致性/规范/安全/测试覆盖五组条款）；评审意见逐条闭环（接受修改/有理拒绝），结论只有"通过/修改后通过/打回"。
- 输出：评审记录（含条款勾选与意见闭环状态）。
- 责任角色：评审负责人 A，开发工程师/Agent R（整改）。

> 🤖 智能体执行要点
> - Agent 作为评审方时按检查单逐项核对并输出条款级结论，禁止只给"LGTM"；
> - Agent 作为被评审方时，对人类评审意见逐条回复处置结果（已改：提交号 / 拒绝：理由）。

### 6.5 接口契约管理

- 输入：详细设计中的接口定义、ADR。
- 执行要点：
  1. 所有跨模块/跨服务接口登记入《接口契约清单》（按 [[12-模板与检查单集]]《接口契约模板》），含：接口 ID、提供方/消费方、协议与格式、错误码表、版本、变更历史；
  2. 契约变更 = 配置项变更，走 SPC-06 变更流程；破坏性变更（删字段、改语义、改错误码）必须升主版本并通知全部消费方，提供方保留旧版本至消费方迁移完成；
  3. 契约即测试基准：每个接口契约至少对应一组契约测试（正常/边界/错误三类用例），随 CI 运行；
  4. 对外部系统（第三方/硬件/遗留系统）的接口，以契约文档 + 真实联调记录双重确认，不允许仅凭猜测对接。
- 输出：接口契约清单、契约测试用例、变更通知记录。
- 责任角色：提供方开发工程师 R，架构师 C，集成负责人 I。

> 🤖 智能体执行要点
> - 调用他方接口前必读契约清单对应条目；契约未记载的字段/行为不得使用；
> - 发现实际响应与契约不符时，记录差异并报告人类负责人，不得自行"适配"掩盖差异。

### 6.6 产品集成（顺序与环境）

- 输入：通过评审的组件 CI、接口契约清单、集成计划。
- 执行要点：
  1. 集成顺序按《集成计划模板》显式定义：自底向上（先工具层/数据层，再业务层，再接入层）为原则；接口依赖冲突时以契约清单的依赖关系排拓扑序，集成顺序写入计划并作为 CI 编排依据；
  2. 集成环境独立于开发环境与生产环境，配置（版本、参数、数据基线）按 SPC-06 管理；集成环境准入：待集成组件已通过静态检查与单元测试；
  3. 每完成一个集成增量，执行接口契约测试 + 集成冒烟用例，结果记录于集成记录单；失败则停止后续增量，先定位（接口不符优先对照契约清单排查）；
  4. 集成完成后移交 SPC-05 验证与确认流程，交接物：可运行构建版本、集成记录单、已知问题清单。
- 输出：集成计划、集成记录单、可运行的集成版本。
- 责任角色：集成负责人 A/R，开发工程师/Agent R（脚本与修复）。

> 🤖 智能体执行要点
> - 集成脚本（构建/部署/冒烟）交由 Agent 执行时，必须逐条输出命令与退出码；任何非零退出即停止并报告，不得自动重试掩盖失败；
> - 禁止在集成环境直接改代码"调试通过"，修复必须回到代码库走 6.3/6.4 流程。

## 7. 出口准则与质量门

本规程设两个质量门，逐项可判定：

QGate-D（设计完成门）：
1. 架构说明文档评审通过；ADR 覆盖全部跨模块决策，无"提议"状态滞留超 5 个工作日；
2. 详细设计满足 6.2 最低颗粒度全部 5 条；需求-设计映射表覆盖率 100%（每个需求条目至少映射一个设计元素）；
3. 技术选型类决策均有 DAR 决议记录（链接到 SPC-10 台账）。

QGate-I（集成完成门）：
1. 主干代码 100% 经 6.4 评审，评审记录齐全、意见全闭环；
2. 静态检查与单元测试在 CI 上全绿；静态检查高危告警为零；
3. 接口契约清单与实际代码一致，契约测试全通过；
4. 集成记录单显示所有增量按序完成，无未闭环的集成失败项；
5. 度量数据（第 8 章）已按口径落盘。

## 8. 度量指标与量化要求

### 8.1 度量项与口径

| 指标 | 计算口径 | 采集点 |
| --- | --- | --- |
| 设计评审缺陷密度 | 设计评审发现的缺陷数 / 设计文档页数（或接口数） | 评审记录 |
| 代码评审缺陷密度 | 评审缺陷数 / 千有效行（KLOC） | 评审记录+代码库 |
| 静态检查告警密度 | 高危+中危告警数 / KLOC | CI 报告 |
| 评审覆盖率 | 经评审代码行 / 全部合入行 | CI/代码库 |
| 接口契约一致率 | 契约测试通过接口数 / 契约接口总数 | 契约测试报告 |
| 集成一次通过率 | 首个增量即通过的集成次数 / 总集成次数 | 集成记录单 |
| 返工率 | 评审/集成打回导致的返工工时 / 开发总工时 | 工时系统 |

### 8.2 示例基线与控制限

- 参考 PPB（过程性能基线）示例：代码评审缺陷密度均值 4.2 个/KLOC，控制限 UCL=7.0 / LCL=1.4；集成一次通过率均值 82%，控制限 ±3σ；静态检查高危告警密度均值 0.15 个/KLOC。
- 控制图应用：按周将上述指标绘入 XmR 控制图；连续 7 点同侧或单点出限即触发 SPC-09 根因分析；基线每季度由度量负责人用最近 12 周稳定数据重算。

### 8.3 PPM 应用（概念性）

- 建立 PPM（过程性能模型）：以"评审缺陷密度、静态告警密度、评审覆盖率"为自变量预测"集成一次通过率"，用于在设计编码阶段预判集成风险；预测低于基线均值时，加严 6.4 评审条款或增加契约测试用例。
- PPM 每半年用实际数据校验一次拟合度，偏差超 20% 时修订模型。

### 8.4 根因分析（CAR）回流

- 设计编码阶段发现的 P1/P2 级缺陷，每月由质量负责人按 SPC-09 做根因聚类（按注入阶段：需求/设计/编码/集成）；出现频次最高的根因类别必须产出至少一条过程改进项（改模板、改检查单、改规范），改进项回流至本规程或 [[12-模板与检查单集]] 并在变更记录中注明。

### 8.5 持续优化（OPM）

- 每季度由过程资产组评审本章指标趋势：稳定在控制限内且业务目标变化时，上调目标值（如评审缺陷密度目标收紧 10%）；新工艺/工具（含 Agent 新用法）经小范围试点并量化对比后方可全面部署，部署结论写入 SPC-01 过程资产库。
- 数据落盘位置建议：度量原始数据存项目仓库 `metrics/` 目录（CSV，按周一个文件），PPB/控制图与 PPM 版本存组织级度量库（见 SPC-08），集成记录与评审记录存配置库（SPC-06）。

## 9. 裁剪指南

| 项目级别 | 判定 | 最小执行集 | 完整执行集 |
| --- | --- | --- | --- |
| 小型/低风险（<2 人月，无跨团队接口） | 规模与风险双低 | ADR 仅记架构级决策；详细设计给接口签名+映射表；静态检查+单测必做；评审可一人交叉；集成计划可并入开发计划；度量只采评审覆盖率、静态告警密度 | 可选 |
| 标准项目 | 默认 | 第 6 章全部活动；度量采 8.1 全部指标；控制图按周 | 即完整集 |
| 大型/高风险（跨团队、安全关键、合规要求） | 任一项命中 | 不允许裁剪 | 完整集 + 契约测试强制三类用例全覆盖 + 每个集成增量出正式记录单 + 度量按日采集 + PPM 预测强制使用 |

裁剪决策须在项目计划（SPC-03）中书面记录并经 QA（SPC-07）确认；小型项目合并的产出物不得删除对应 QGate 条款，仅允许简化载体形式。
