# SPC-06 《06-配置与变更管理规程》

> 版本：v1.0　生效日期：2026-09-17　密级：内部　所属体系：软件过程体系（CMMI-L5）

## 1. 目的

建立配置管理（Configuration Management，CM）与变更控制的统一规程，确保软件工作产品在整个生命周期内：标识唯一、版本可溯、基线可控、变更受审、状态可查、介质可恢复。本规程是"人机混合团队"下防止 Agent 无序改动、防止配置漂移、防止变更失控的操作级依据。

量化目标（组织级 OPP 基线，见 SPC-08）：
- 变更闭环率（已关闭变更 / 已批准变更）≥ 98%；
- 变更回退率（验证不通过或引发缺陷的变更 / 已实施变更）≤ 5%；
- 配置审计不符合项密度 ≤ 2 项 / 每 100 CI；
- 任一仓库恢复时间目标（RTO）≤ 4 小时，恢复点目标（RPO）≤ 24 小时。

## 2. 适用范围

适用于本团队所有软件项目及其衍生工作产品，包括：源代码、构建脚本、数据库脚本与结构、需求/设计/测试文档、接口契约、部署配置（`.env.example`、nginx conf、启动脚本）、发布制品（APK/JAR/WAR）、以及项目级过程资产（模板、检查单、基线记录）。

约束范围说明：含口令、密钥、证书私钥的文件不属于常规 CI，按密件管理，只登记"存在性与版本号"，不登记内容；任何工具不得将其内容提交至版本库。

执行主体为人类工程师与 AI 智能体（Agent）。Agent 执行本规程中与人类相同的判定与留痕要求，不得以"自动执行"为由跳过 CCB（变更控制委员会）批准或质量门。

## 3. 体系定位与 CMMI 实践域映射

三级体系定位：本规程是二级"规程"文件，上承《SPC-00 总纲手册》的配置管理方针，下接《SPC-12 模板与检查单集》中的变更申请单、基线发布单、配置审计检查单、备份恢复演练记录等模板。

覆盖的 CMMI v3.0 实践域及等级：

| 实践域 | 成熟度等级 | 本规程覆盖要点 |
| --- | --- | --- |
| CM（Configuration Management） | 2 级 | CI 识别、基线建立、变更控制、状态报告、配置审计 |
| CM | 3 级 | 组织级 CI 命名标准、基线策略标准、跨项目统一工具链 |
| MPM（Managing Performance & Measurement） | 4 级 | 变更回退率、审计缺陷密度的 PPB（过程性能基线）监控 |
| CAR（Causal Analysis & Resolution） | 5 级 | 对回退变更、配置事故做根因分析并回流过程资产 |
| OPM（Optimizing Performance & Management） | 5 级 | 基于度量数据优化分支策略、发布节奏与备份方案 |

与其他规程的接口：需求变更的提出与追踪走 SPC-02；变更对进度/资源的量化影响评估走 SPC-03；实施与验证走 SPC-04、SPC-05；度量数据上报走 SPC-08；根因分析走 SPC-09；风险登记走 SPC-10。

## 4. 术语与角色

术语：
- CI（Configuration Item，配置项）：被单独标识、纳入版本控制的工作产品单元。
- 基线（Baseline）：一组经正式批准的 CI 版本组合，是后续变更的参照点；分功能基线、分配基线、产品基线。
- CCB（Change Control Board，变更控制委员会）：变更审批的责任实体，可由一人兼多角色（小项目裁剪）。
- PPB（Process Performance Baseline，过程性能基线）：历史过程数据的统计特征（均值、控制限），用于判断过程是否稳定。
- Agent（智能体）：承接任务的 AI 执行体（如 Kimi Code、Claude Code），须遵守与人类相同的质量门与审批链。
- RTO/RPO：恢复时间目标 / 恢复点目标。

RACI 简表：

| 活动 | 项目经理 | 配置管理员（CMO） | 开发（人/Agent） | CCB | QA |
| --- | --- | --- | --- | --- | --- |
| CI 识别与命名 | A | R | C | I | C |
| 基线建立 | A | R | I | C | C |
| 变更申请 | I | C | R | I | I |
| 变更批准 | A | C | I | R | C |
| 变更实施 | I | C | R | I | I |
| 配置审计 | I | R | C | I | A |
| 备份与恢复演练 | A | R | C | I | C |

R=执行，A=批准，C=咨询，I=知会。

## 5. 入口准则

满足以下条件，项目方可启动配置管理活动：

1. 项目已立项，仓库与目录结构已按 SPC-01 的裁剪结果确定（详见 SPC-12《配置管理计划模板》）。
2. 已指定配置管理员（CMO）或明确其职责由项目经理兼任。
3. 版本库可用（git 远程或本地裸库），`.gitignore` 已包含密钥、构建产物、依赖目录、个人环境文件。
4. 初始 CI 清单已登记（可随首个基线一并建立）。

## 6. 过程活动

### 6.1 配置项识别与命名

- 输入：项目策划输出（SPC-03）、需求基线草案、仓库目录结构。
- 执行要点：
  1. CMO 牵头编制《CI 清单》（SPC-12 模板），每条 CI 记录：CI 标识、名称、类别（代码/文档/脚本/配置/制品）、负责人、入库路径。
  2. CI 命名规则：`<类别码>-<项目码>-<名称>-<版本段>`，类别码取值 SRC/DOC/SCR/CFG/BLD；文件内版本段只在正式文档 CI 使用，代码 CI 一律以 git 提交哈希与 tag 为准，文件名不得带"最终版/最新版/v2改"字样。
  3. 每一个进入基线的 CI 必须有唯一负责人；无主 CI 不得入基线。
- 输出：《CI 清单》v1，作为功能基线的一部分。
- 责任角色：CMO（R），项目经理（A）。

> 🤖 智能体执行要点：Agent 新建文件前先 `Glob`/`ls` 确认同目录无同类文件，避免产生 `xxx_copy.md`、`xxx-新.md` 这类无主副本；不得创建临时文档式 CI（总结稿、汇报稿）除非任务明确要求；新建 CI 后在其归属目录的索引文件（README 或台账）中登记一行。

### 6.2 基线类型与建立时机

三类基线定义与时机：

| 基线类型 | 内容 | 建立时机 | 批准人 |
| --- | --- | --- | --- |
| 功能基线 | 需求规格说明、接口契约、验收准则 | 需求评审通过时（SPC-02 出口） | 项目经理+客户代表 |
| 分配基线 | 架构设计、详细设计、数据库设计、测试计划 | 设计评审通过时（SPC-04 出口） | 项目经理 |
| 产品基线 | 可交付制品、安装包、发布说明、用户文档 | 验收测试通过、正式发布前（SPC-05 出口） | CCB |

- 执行要点：
  1. 建立基线=登记《基线发布单》（SPC-12 模板）+ 在 git 打 tag（tag 名 `<项目码>-BL-<类型>-<日期>-<序号>`，如 `APS-BL-P-20260901-01`）。
  2. 基线建立后，其 CI 的任何修改都必须走 6.3 变更流程，不允许"基线外悄悄改"。
  3. 基线清单每月由 CMO 核对一次，与仓库 tag 列表对账，差异写入配置状态报告。
- 输出：《基线发布单》、git tag、配置状态报告条目。

> 🤖 智能体执行要点：Agent 不得擅自创建、删除、移动 tag；任务结束汇报时必须给出本次改动涉及的提交哈希或文件版本说明，便于 CMO 核对基线一致性。

### 6.3 变更控制 CCB 流程

标准流程六步：**申请 → 影响分析 → 批准 → 实施 → 验证 → 关闭**。

1. 申请：任何已基线化 CI 的修改需求，提出人填写《变更申请单》（SPC-12 模板），字段：变更编号（CR-YYYYMMDD-NN）、涉及 CI、变更原因、期望完成时间。紧急修复可先行口头申请，24 小时内补单。
2. 影响分析：由熟悉该 CI 的开发（人或 Agent）执行，输出《影响分析报告》：涉及的 CI 清单、对功能/接口/进度/测试用例的影响、回归测试范围、工作量估计、风险（登记 SPC-10 风险台账）。影响分析不通过的变更（不可行/代价过大）由 CCB 直接驳回。
3. 批准：CCB 按变更等级决策——一般变更（不涉及已基线化接口与需求）项目经理批准；重大变更（动功能基线、动已发布接口、工作量>3 人日）CCB 会议批准。审批结论三态：批准/驳回/暂缓（须写明理由）。
4. 实施：开发按批准方案实施，实施前先建备份（见 6.8）；实施记录写入变更单"实施记录"栏：实际改动文件、提交哈希、自测结果。
5. 验证：按影响分析报告圈定的回归范围执行验证（SPC-05），验证人与实施人分离（Agent 实施则由人或另一 Agent 验证）。验证结论：通过/不通过（不通过则回退至基线版本并重走流程）。
6. 关闭：验证通过后 CMO 更新配置状态报告，变更单置"关闭"，同步更新受影响的文档 CI 与关联需求追踪（SPC-02）。未关闭变更不得被宣告完成。

- 输入：《变更申请单》、当前基线清单；输出：闭环的变更单、更新后的 CI 与配置状态报告。

> 🤖 智能体执行要点：① Agent 接到"改某个已基线化文件"的任务时，先确认变更单编号；无编号且改动触及基线 CI 的，在动手前向派单方索取批准记录，或在任务记录中标注"本次属未基线化内容/文档类微调"；② 实施环节严格遵守项目惯例——改动前先生成 `文件名.bak` 备份（模板、HTML、配置文件等高风险文件），大型改造（多文件结构性调整）前输出整目录备份或 git 提交快照说明；③ 不得执行 git 变更类操作（commit/push/reset/rebase/tag/branch 切换）除非任务明确授权；④ 实施记录必须包含可复核证据：运行的测试命令与其结果。

### 6.4 版本与分支策略

- 版本号：发布制品采用语义化版本 `主版本.次版本.修订号+构建号`（如 1.7.1+22）；主版本=不兼容变更，次版本=向后兼容功能，修订号=缺陷修复。
- 分支模型（完整集，中型以上项目）：`main`（产品基线，仅接受合并）/ `develop`（集成分支）/ `feature/<变更编号>` / `hotfix/<缺陷编号>`。小型项目裁剪为 `main` + 短生命周期 `feature` 分支（SPC-01 裁剪表执行）。
- 执行要点：
  1. 分支名必须挂变更编号或缺陷编号，便于追溯；无编号分支视为无主改动，评审时不予合并。
  2. 合并到 main 前必须通过：构建通过、项目标准测试命令全绿、代码评审记录存在。
  3. 分支合并后删除，仓库分支数控制在活跃工作范围内（建议 ≤ 10）。
- 责任角色：开发（R）、CMO（A 对 main 合入门禁）。

> 🤖 智能体执行要点：Agent 默认在当前分支就地修改并给出 diff 级交付；如需建分支必须获得任务明示；禁止 `git reset --hard`、`git push --force` 等不可逆命令，发现需要此类操作时停下来向派单方报告。

### 6.5 发布管理

- 触发：产品基线达成（6.2 第三类）后进入发布流程。
- 执行要点：
  1. 编制《发布说明》（SPC-12 模板）：版本号、含变更清单（链接变更单）、已知问题、升级/回退步骤、校验信息（文件大小、哈希）。
  2. 发布制品归档双副本：本地归档目录 + 远程站点/制品库；制品命名含完整版本号，禁止覆盖同名旧制品。
  3. 线上发布须留回退通道：保留前一版本制品与配置快照，回退操作步骤在发布说明中可照抄执行。
  4. 发布后 CMO 更新配置状态报告，并将版本号写入项目版本台账。
- 输出：《发布说明》、归档制品、更新后的版本台账。

> 🤖 智能体执行要点：发布脚本/上传脚本执行前，Agent 必须确认：①凭据不写入脚本与日志（密码走 argv 或环境变量）；②上传后做外部可达性验证（如 HTTP 200、版本号文件核对）并把验证输出写入任务记录。

### 6.6 配置状态报告与配置审计

- 状态报告：CMO 每月（或每个里程碑）输出《配置状态报告》：CI 总数、基线清单、变更统计（申请/批准/驳回/关闭/回退）、版本台账摘要。数据落盘到项目 `docs/` 或知识库过程资产目录，供 SPC-08 汇总。
- 配置审计两类：
  1. 功能配置审计（FCA）：验证 CI 内容满足其基线化需求——结合 SPC-05 的验证记录核对，每个产品基线一次。
  2. 物理配置审计（PCA）：验证仓库实物与台账一致——CI 清单对账、tag 对账、无主文件清理、密钥泄漏扫描（grep 高危模式如密码/私钥）。每季度一次，发布前加做一次。
- 不符合项处理：登记《审计不符合项清单》，限期整改；重复出现的不符合项转入 SPC-09 根因分析。

> 🤖 智能体执行要点：PCA 中的对账、扫描类任务可由 Agent 执行：用 `Grep` 扫描密钥模式、用 git 命令列 tag 与台账比对、列出未被清单登记的孤儿文件；审计产出直接写入《审计不符合项清单》模板，不得只口头汇报。

### 6.7 备份与恢复

- 备份策略：版本库远程镜像（首选）+ 每周全量打包归档（含数据库导出）；知识库与文档类资产纳入目录级备份。3-2-1 原则：3 份副本、2 种介质、1 份异地。
- 执行要点：
  1. 备份清单（备什么、频率、落点、责任人）写入《配置管理计划》；新增项目时同步新增备份条目。
  2. 恢复演练每半年一次：随机抽一个仓库/数据库备份做真实恢复并验证可用（能构建/能查询），结果记录《备份恢复演练记录》（SPC-12 模板），实测 RTO/RPO 与第 1 节目标比对。
  3. 单文件级"改动前备份"惯例：凡对高风险文件（模板、配置、长文档、线上脚本）做修改，先复制 `文件名.bak`（或带日期的 `.bak-YYYYMMDD`），变更验证通过后由下次清理任务统一回收。
- 责任角色：CMO（R 对仓库与目录备份）、实施人（R 对改动前文件备份）。

> 🤖 智能体执行要点：Agent 的任何修改动作遵循"可回退优先"：大改（>3 文件或结构性调整）前先确认存在 git 干净基线或手工备份，没有则先创建再动手；`.bak` 文件命名带日期，并在任务记录中列出备份路径。

## 7. 出口准则与质量门

项目配置管理活动的 QGate 判定清单：

1. CI 清单与仓库实物一致，孤儿文件率 ≤ 2%（PCA 实测）。
2. 三类基线按 6.2 时机全部建立，tag 与《基线发布单》一一对应。
3. 已批准变更 100% 走完六步流程，变更闭环率 ≥ 98%。
4. 变更回退率 ≤ 5%；超标即触发 SPC-09 根因分析。
5. 版本台账完整，任一发布制品可按版本号找回对应源码提交。
6. 备份清单有效，最近一次恢复演练 RTO ≤ 4h、RPO ≤ 24h。
7. 仓库中无明文密钥（PCA 扫描零命中）。
8. Agent 参与的任务均有可复核的实施记录（提交哈希/备份路径/测试结果）。

## 8. 度量指标与量化要求

数据落盘建议：配置状态报告与变更台账存项目 `docs/` 目录；组织级汇总入 SPC-08 的度量数据库（或台账表），月度更新。

| 指标 | 计算口径 | 采集频率 | 示例基线/控制限 |
| --- | --- | --- | --- |
| 变更闭环率 | 已关闭变更数 / 已批准变更数 | 月 | PPB：均值 99%，下限 95% |
| 变更回退率 | 验证不通过或上线后回退的变更数 / 已实施变更数 | 月 | PPB：均值 2.8%，上限 5% |
| 平均变更周期 | 变更单"申请→关闭"日历天均值（按重大/一般分开统计） | 月 | 一般变更 P50 ≤ 3 天 |
| 审计不符合项密度 | PCA/FCA 不符合项数 / 受审 CI 数 ×100 | 季度 | 上限 2 项/100 CI |
| 孤儿文件率 | 未登记 CI 的受控目录文件数 / 文件总数 | 季度 | ≤ 2% |
| 备份有效性 | 恢复演练成功次数 / 演练次数；实测 RTO、RPO | 半年 | 100%；RTO ≤ 4h |
| 密钥泄漏事件 | PCA 扫描命中数 | 季度 | 0（硬指标） |

L4/L5 应用方式：
- 控制图：对"变更回退率""平均变更周期"按项目月度打点，数据落在 PPB 控制限外（连续 3 点同侧漂移或单点越限）即判为特殊原因，转 SPC-09 做根因分析（CAR）。
- PPM（过程性能模型）概念性应用：以"影响分析耗时、回归范围大小、变更规模"为因子预测变更周期与回退风险，用于 CCB 排期与验证资源安排；模型每半年用新数据校准一次，由过程资产组维护。
- 改进回流：CAR 结论（如"回退高发于跨模块接口变更"）转化为过程资产更新——修订 6.3 影响分析检查项、调整裁剪表，由过程资产组评审后升版本，并通知全部 Agent 的使用方更新执行要点。

## 9. 裁剪指南

按项目规模/风险分级（判定标准见 SPC-01 §裁剪决策表）：

| 级别 | 适用 | 最小执行集 |
| --- | --- | --- |
| 小型/低风险（<1 人月、单模块、无对外接口） | 工具脚本、内部实验 | CI 清单（简表）；功能+产品两类基线（分配基线并入产品基线）；变更走"申请→批准→实施→验证→关闭"五步（影响分析并入申请单）；单分支 main；发布说明从简（版本+变更列表）；改动前 .bak 惯例保留 |
| 中型/中风险 | 常规业务系统 | 本规程全文，CCB 可由"项目经理+技术负责人"两人构成 |
| 大型/高风险（多模块、对外发布、合规要求） | 交付型产品 | 本规程全文 + CCB 正式会议制 + 每次发布前 PCA 加审 + 恢复演练季度化 |

不可裁剪项（任何级别）：改动前备份惯例、禁止 Agent 擅自执行 git 变更类操作、密钥不入库、变更验证人与实施人分离。
