# SPC-08 《08-度量分析与组织过程性能规程》

> 版本：v1.0　生效日期：2026-09-17　密级：内部　所属体系：软件过程体系（CMMI-L5）

## 1. 目的

本规程定义组织的度量体系与组织过程性能（Organizational Process Performance, OPP）管理方法，目标：

1. 建立统一、可汇总、可追溯的组织度量集，使规模、工作量、缺陷、进度、质量五族数据在人与智能体（Agent）混合团队中以同一口径产生；
2. 建立并维护过程性能基线（Process Performance Baseline, PPB），为项目量化管理（SPC-03）、统计过程控制（Statistical Process Control, SPC）与根因分析（SPC-09）提供量化依据；
3. 建立过程性能模型（Process Performance Model, PPM）的概念模型与使用场景，支持"以数定策"的目标协商与方案预测；
4. 使度量活动本身可执行、可判定：谁采集、何时采集、落盘何处、谁分析、多久一次、结论回流到哪个过程资产，均有明确指令。

## 2. 适用范围

- 适用于组织内全部软件研发项目、维护任务与智能体承接任务（含代码生成、测试、文档、部署脚本类任务）。
- 适用于过程资产组（PAT）、项目负责人（PM）、质量保证（QA）、度量分析员、人类工程师与 Agent。
- 不适用于纯商务、行政类工作的度量；安全类事故度量另按 SPC-10 管理。

## 3. 体系定位与 CMMI 实践域映射

- 体系位置：三级体系第二级《规程》。上位文件为 SPC-00 总纲手册；本规程向下使用 SPC-12 中的度量模板（度量计划表、PPB 卡片、控制图台账、度量报告模板）。
- 横向衔接：SPC-03 用本规程的 PPB/PPM 做量化策划与监控；SPC-05/07 提供验证与 QA 数据源；SPC-09 以本规程控制图与度量数据作为根因分析输入；SPC-11 规定 Agent 留痕动作，本规程规定留痕数据的格式与汇总口径。
- CMMI v3.0 映射：
  - MA（Measurement and Analysis，度量与分析）：2 级实践全覆盖（度量目标、度量规程、采集存储、分析、报告）。
  - OPP（Organizational Process Performance，组织过程性能）：4 级（PPB 建立与维护、过程性能分析）。
  - QPM（Quantitative Project Management）：4 级（本规程提供其数据与基线供给，执行见 SPC-03）。
  - CAR（Causal Analysis and Resolution）：5 级数据输入方；OPM（Optimizing Performance Management）：5 级数据输入方（执行见 SPC-09）。

## 4. 术语与角色

术语：

- **PPB**：过程性能基线。某一度量项在稳定过程上的期望值与波动区间（均值、标准差、控制限），由历史数据经统计检验后发布。
- **PPM**：过程性能模型。描述输入因子（如复杂度、复用率、评审深度）与输出度量（如缺陷密度、工期偏差）关系的预测模型，本体系阶段采用经验回归/查表式概念模型。
- **SPC**：统计过程控制。用控制图区分普通原因波动与特殊原因变异的方法。
- **CI**：配置项。**QGate**：质量门。**Agent**：智能体，承接任务的 AI 执行体（如 Kimi Code、Claude Code），须遵守与人类相同的质量门，并按本规程 §6.2 留痕度量数据。
- **控制限**：UCL/LCL（上/下控制限），通常为 μ±3σ，由 PPB 给出。

RACI 简表：

| 活动 | PAT（过程资产组） | PM | QA | 工程师/Agent | 度量分析员 |
|---|---|---|---|---|---|
| 组织度量集定义与修订 | A | C | C | I | R |
| 任务级数据采集留痕 | I | A | C | R | I |
| 数据质量检查 | I | C | R | C | R |
| PPB 建立与年度刷新 | A | C | C | I | R |
| 控制图分析与判异处置 | I | R | C | I | A/R |
| 度量报告发布 | A | C | I | I | R |

（R=执行 A=批准 C=咨询 I=知会；Agent 在"工程师/Agent"列承担 R，其留痕正确性由提交任务的 PM/工程师复核。）

## 5. 入口准则

同时满足以下条件方可启动一个项目/批次的度量执行：

1. 项目或任务批次已按 SPC-03 立项，有明确的任务台账（任务分解到可留痕粒度：单任务工作量 ≤ 40 人时或 ≤ 8 机时）。
2. 已依据本规程 §9 确定裁剪级别，度量计划（选用 SPC-12《度量计划表》模板）经 PM 批准。
3. 度量工具与落盘位置就绪：任务记录文件、工时/缺陷字段、汇总脚本路径明确（默认见 §8.4）。
4. 当年度 PPB 已发布且在有效期内（新项目首个迭代允许使用组织默认 PPB，并在度量计划中注明）。

## 6. 过程活动

### 6.1 组织度量集定义与维护

- **输入**：组织过程资产现状、上年度度量数据、业务目标（质量/交付/成本类）。
- **执行要点**：
  1. PAT 按 §8.1 五族度量集逐项确认：度量项名称、定义、计算口径、单位、数据源、采集频率，写入组织《度量集定义表》（SPC-12 模板）。
  2. 每个度量项必须有唯一编号（形如 `M-SIZE-01`）与"为什么度量它"的目标句，无目标的度量项删除。
  3. 度量项的新增/停用/口径变更走 SPC-06 配置变更流程，变更后历史数据的可比性结论（可比/需换算/断层）须在定义表备注。
- **输出**：《度量集定义表》（CI，版本受控）。
- **责任角色**：PAT（A/R），度量分析员（R）。

### 6.2 任务级数据采集与留痕

- **输入**：任务台账、进行中的任务记录。
- **执行要点**：
  1. 每个任务在**关闭时**（而非回忆补录）记录：计划工时/实际工时、缺陷数（按注入阶段分类）、返工工时、交付规模（代码行/功能点/文档页）、任务起止日期。
  2. 采集点为流程天然节点：任务关闭、代码合并、缺陷关闭、版本发布、迭代评审，不新增额外填报动作。
  3. 自动化优先：优先从 git 历史、CI 流水线日志、任务系统导出；手工填报项在度量计划中标出并控制在 5 项以内。
- **输出**：逐任务的度量记录（格式见 §6.2.1）。
- **责任角色**：工程师/Agent（R），PM（A 复核）。

#### 6.2.1 任务度量记录统一格式（人与 Agent 共用）

每条任务记录为一段 YAML 块，附于任务记录文件尾部或集中存于 `metrics/tasks/<任务ID>.yml`：

```yaml
task_id: PROJ-2026-0142
executor: agent:kimi-code | human:张三        # 执行体类型+标识
planned_hours: 6.0
actual_hours: 7.5                              # Agent 任务记"机时当量"：会话累计时长
rework_hours: 1.0                              # 因缺陷或需求变更产生的重做工时
defects_found_pre: 0                           # 交付前自检发现并修复的缺陷
defects_found_post: 2                          # 交付后（评审/测试/上线）发现的缺陷
size: {code_lines: 480, docs_pages: 0, config_items: 3}
start: "2026-09-15T09:30+08:00"
end: "2026-09-15T17:00+08:00"
linked_change: CR-0031                         # 关联变更单，无则 null
```

> 🤖 **智能体执行要点**
>
> - 任务结束交付前，Agent **必须**在当前任务记录中追加上述 YAML 块；缺字段视为任务未关闭，不得报告"完成"。
> - `actual_hours` 用会话实际累计时长；无法精确计时按"会话轮数 × 平均轮时长"估算并在字段后加 `(est)` 标注。
> - `defects_found_pre` 记交付前自检（构建失败、测试红、lint 告警修复）次数；`rework_hours` 记因需求理解偏差返工的部分。
> - 数字一律用半角、小时保留 1 位小数、时间用 ISO 8601 带时区；禁止写"约/大概"类文字。

### 6.3 数据汇总与质量检查

- **输入**：任务度量记录、git/CI 自动采集数据。
- **执行要点**：
  1. 度量分析员每周执行汇总脚本，生成项目周度度量表；每月生成组织级汇总。
  2. 汇总前跑数据质量检查（§8.3 规则），不合格记录退回记录人限期 2 个工作日补正；补正后重跑汇总。
  3. 汇总脚本与规则同属 CI，纳入 SPC-06 管理；口径修改必须同步改《度量集定义表》。
- **输出**：周度/月度度量汇总表（CSV + 渲染报告）。
- **责任角色**：度量分析员（R），QA（数据质量 C/R 抽查）。

### 6.4 PPB 建立、发布与年度刷新

- **输入**：连续 ≥ 6 个月且经质量检查合格的组织度量数据。
- **执行要点**：
  1. 按度量项计算均值 μ、标准差 σ；用控制图剔除特殊原因点（先判异、剔除有据点、再重算），得到稳定过程下的 μ、σ 与 μ±3σ 控制限。
  2. 样本量 < 20 个项目/迭代点的度量项不发布 PPB，只发布参考区间并注明"数据积累中"。
  3. 每张 PPB 写入《PPB 卡片》（SPC-12 模板）：度量项、样本期间、n、μ、σ、UCL/LCL、剔除点与理由、适用过程范围。
  4. **刷新节奏**：每年一次全面刷新（固定在第 4 季度）；过程发生批准的变更（工具链更换、Agent 大规模引入等）后，相关 PPB 挂"待重订"标记，积累 ≥ 8 个新数据点后重算。
- **输出**：年度《组织 PPB 集》（CI）；项目量化目标（供 SPC-03）。
- **责任角色**：度量分析员（R），PAT（A）。

### 6.5 控制图分析与判异处置

- **输入**：周/月度度量数据、现行 PPB。
- **执行要点**：
  1. 对核心度量项（缺陷密度、工期偏差率、返工率、评审缺陷检出率）按项目或迭代打点控制图（单值图 I-chart 为主）。
  2. **判异规则**（命中任一条即判特殊原因，须处置）：
     - R1：单点超出 UCL 或低于 LCL；
     - R2：连续 7 点落在中心线同侧；
     - R3：连续 7 点单调上升或下降；
     - R4：连续 14 点上下交替；
     - R5：3 点中 2 点落在 μ±2σ 之外（同侧）。
  3. 判异后 5 个工作日内启动分析：由度量分析员出具初步判定（数据错误/特殊原因/过程漂移），确认为特殊原因的按 SPC-09 转根因分析；数据错误退回 §6.3。
  4. 处置结论（含"无需行动"结论）记录于《控制图台账》，不得静默忽略。
- **输出**：控制图台账条目；必要时 CAR 立项单。
- **责任角色**：度量分析员（A/R），PM（R 处置），QA（C）。

### 6.6 PPM 概念模型建立与使用

- **输入**：PPB 集、项目历史属性（复杂度、复用率、团队构成、Agent 参与度）。
- **执行要点**：
  1. 本阶段采用**概念模型 + 查表/经验回归**两档：
     - 查表档：按项目属性分桶（规模×复杂度×Agent 参与度），每桶给出缺陷密度/工期偏差的 PPB 分位数表；
     - 回归档：数据量足够（n ≥ 30）的度量项可拟合线性/多元回归模型，模型须记录 R² 与残差图结论。
  2. **使用场景限定**：a) 立项时质量/工期目标的量化协商（SPC-03）；b) 重大方案比选的预测（如"引入 Agent 结对 vs 纯人工"的预期缺陷密度差）；c) 中段"能否达标"的预测预警。
  3. PPM 预测结果必须带置信区间，禁止只报点估计；预测偏差（实际-预测）回流入 PPM 校准记录。
  4. PPM 与 PPB 同周期评审；模型失效（预测偏差连续 3 次超区间）即降级回查表档。
- **输出**：《PPM 卡片》（模型式/分桶表、适用范围、校准记录）。
- **责任角色**：度量分析员（R），PAT（A）。

### 6.7 度量报告与改进回流

- **输入**：周/月度汇总、控制图台账、PPB/PPM 使用情况。
- **执行要点**：
  1. 报告节奏：**周报**（项目级，项目例会用，1 页）→ **月报**（组织级，度量分析员发布）→ **季度评审**（PAT 主持，PPB/PPM 健康度 + 改进候选清单）。
  2. 季度评审必须产出下列之一：PPB 修订项、PPM 校准项、度量项增删项、转 SPC-09 的改进/根因立项项；无产出须在纪要中说明理由。
  3. 所有改进结论回流至过程资产：更新《度量集定义表》、PPB 集、相关规程（按 SPC-01 变更流程）。
- **输出**：度量周报/月报、《季度度量评审纪要》。
- **责任角色**：度量分析员（R），PAT（A）。

## 7. 出口准则与质量门

度量活动 QGate（项目结项或年度评审时判定）：

- [ ] 本项目全部已关闭任务均有 §6.2.1 格式度量记录，数据质量抽查合格率 ≥ 95%；
- [ ] 核心度量项控制图齐全，判异点 100% 有台账处置结论；
- [ ] 项目实际值与 PPB 的偏差分析已写入结项报告；
- [ ] 组织层面：年度 PPB 刷新完成并发布；季度评审纪要齐全，改进项均有去向（资产更新单或 SPC-09 立项单）；
- [ ] 《度量集定义表》《组织 PPB 集》《PPM 卡片》均处于受控基线且版本一致。

## 8. 度量指标与量化要求

### 8.1 组织度量集（五族）

| 族 | 编号 | 度量项 | 计算口径 | 单位 |
|---|---|---|---|---|
| 规模 | M-SIZE-01 | 代码规模 | 新增+修改物理行（cloc 口径，剔除自动生成文件） | LOC |
| 规模 | M-SIZE-02 | 交付功能点 | 简化功能点（按页面/接口/批处理计数，规则见定义表附录） | FP |
| 工作量 | M-EFF-01 | 实际工时 | 任务关闭时填报；Agent 记机时当量 | 人时/机时 |
| 工作量 | M-EFF-02 | 返工率 | 返工工时 ÷ 实际总工时 | % |
| 缺陷 | M-DEF-01 | 缺陷密度 | 交付后缺陷数 ÷ 规模（每 KLOC 或每 FP） | 个/KLOC |
| 缺陷 | M-DEF-02 | 缺陷注入分布 | 按注入阶段（需求/设计/编码/集成）占比 | % |
| 缺陷 | M-DEF-03 | 自检拦截率 | 交付前自检发现数 ÷（自检发现+交付后发现） | % |
| 进度 | M-SCH-01 | 工期偏差率 | （实际工期-计划工期）÷ 计划工期 | % |
| 进度 | M-SCH-02 | 里程碑准点率 | 准点里程碑数 ÷ 里程碑总数 | % |
| 质量 | M-QUA-01 | 评审缺陷检出率 | 评审发现缺陷 ÷ 交付前总发现缺陷 | % |
| 质量 | M-QUA-02 | 测试一次通过率 | 首轮测试通过任务数 ÷ 送测任务总数 | % |
| 质量 | M-QUA-03 | 发布回退率 | 回退发布次数 ÷ 发布总次数 | % |

### 8.2 示例基线与控制限（示例值，正式值以当年《组织 PPB 集》为准）

- M-DEF-01 缺陷密度：μ = 4.2 个/KLOC，σ = 1.5 → UCL = 8.7，LCL = 0（下限截断为 0）。
- M-SCH-01 工期偏差率：μ = +8%，σ = 12% → UCL = +44%，LCL = -28%。
- M-EFF-02 返工率：μ = 11%，σ = 5% → UCL = 26%，LCL = 0。
- M-QUA-02 一次通过率：μ = 78%，σ = 9% → UCL = 100%（截断），LCL = 51%。

项目/迭代打点落入控制限内且不满足 §6.5 判异规则 = 过程受控，不采取单点行动。

### 8.3 度量数据质量要求（六性）

1. **完整性**：必填字段无缺失（task_id/executor/工时/起止为必填）；
2. **准确性**：与源系统（git/CI/任务台账）可核对，抽查误差 ≤ 5%；
3. **及时性**：任务关闭后 24h 内留痕，周汇总前补齐；
4. **一致性**：单位、时区、口径符合《度量集定义表》；
5. **唯一性**：task_id 不重复，重开任务追加新记录不覆盖旧记录；
6. **可追溯性**：每条记录可回溯到任务台账与（如有）变更单。

### 8.4 数据落盘位置建议

- 任务级记录：`metrics/tasks/`（每任务一文件）或任务系统自定义字段；
- 周/月汇总：`metrics/summary/YYYY-Www.csv`、`metrics/summary/YYYY-MM.csv`；
- 控制图与台账：`metrics/spc/`；PPB/PPM 卡片：`metrics/ppb/`、`metrics/ppm/`；
- 上述目录随项目入版本库（大文件除外），纳入 SPC-06 基线。

## 9. 裁剪指南

| 级别 | 适用（规模/风险） | 最小执行集 | 完整执行集 |
|---|---|---|---|
| 小型/低风险（< 2 人月，无外部交付） | 内部工具、一次性脚本 | 任务留痕（§6.2，字段可只填 task_id/executor/工时/缺陷）；月汇总；不作控制图 | 增加缺陷注入分布填报 |
| 中型/中风险（2–12 人月） | 常规项目 | 五族核心度量项（M-SIZE-01/M-EFF-01/M-DEF-01/M-SCH-01/M-QUA-02）+ 控制图 R1/R2 规则 + 季度评审参与 | 全度量项 + PPM 查表档用于目标协商 |
| 大型/高风险（> 12 人月或关键交付） | 战略项目、对外交付 | 中型全集 + 全部判异规则 + PPM（含回归档）预测 + 月度 PAT 复核 | 不可裁剪，全部执行 |

裁剪决定由 PM 提出、PAT 批准，记录于度量计划；大型项目的任何裁剪须 QA 会签。
